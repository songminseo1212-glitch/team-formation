# 구현 계획

## 1. 파일 구성
| 파일 | 하는 일 |
|---|---|
| `engine.py` | 규칙 판단(순수 함수). 지원, 투표, 마감, 배정안 검사, 모든 경우를 따지는 배정, 명단 CSV 검사 |
| `db.py` | Supabase 연결 풀, 잠금 트랜잭션, 상태 읽기, engine 결과(ops)를 DB에 적용 |
| `ai.py` | 오픈라우터 호출(모델마다 전체 120초), 프롬프트, 답 해석 |
| `streamlit_app.py` | 로그인, 학생 화면, 관리자 화면 |
| `schema.sql` | tf_ 테이블과 제약 |
| `keepalive.py`, `.github/workflows/keepalive.yml` | 매일 DB 질의(일시정지 막기) |
| `tests/test_engine.py` | 연습용 시나리오 3개를 DB 없이 시험 |

## 2. 설계 원칙
- engine은 DB와 화면을 모른다.
  - 동작 함수는 상태를 받아 (결과 안내, 바꿀 내용 목록)을 돌려준다.
  - 그래서 같은 규칙을 지원할 때와 승인 직전에 그대로 다시 쓰고, 시나리오를 DB 없이 시험할 수 있다.
- 상태를 바꾸는 동작은 db.act 하나로 처리한다.
  - 한 트랜잭션 안에서 잠금을 걸고 → 최신 상태를 읽고 → engine으로 판단하고 → 적용한다.
  - DB 유일성 제약이 마지막 안전망이다.

## 3. 3장 기능별로 고른 해결
| 기능 | 고른 해결 | 구현 |
|---|---|---|
| 다른 사람의 변경 보기 | 어려운 해결 | `st.fragment(run_every=3)` |
| 필수 포함 역할을 지킬 수 없는 팀 | 어려운 해결 | `join_problem`: 남는 자리 수가 아직 못 채운 필수 역할 수보다 적으면 막음(한 학생은 하나로만 셈) |
| 같은 팀에 대기 중인 지원이 여럿 | 어려운 해결 | 마지막 찬성이 들어온 순간 `join_problem`으로 다시 검사 |
| 마지막 자리에 두 명이 동시에 들어감 | 어려운 해결 | `tf_members` 기본 키 (team_id, slot_no)와 student_id unique, advisory lock |
| AI 응답이 늦을 때 | 어려운 해결 | 요청을 별도 스레드에서 돌리고 바깥에서 전체 120초를 재서 끊음 |
| 3차 모델까지 실패 | 어려운 해결 | `solve`: 되추적으로 모든 경우를 따져 다섯 가지 검사를 통과하는 배정을 찾음 |
| AI 대기 중 화면 | 어려운 해결 | assign_status에 "n차 모델 …의 응답을 기다리는 중 · k초"를 1초마다 갱신 |
| DB 일시정지 막기 | 어려운 해결 | GitHub Actions 예약 실행으로 매일 질의 |

## 4. 단계
1. schema.sql 작성 → Supabase에 tf_ 테이블 생성(앱 시작 때 자동 실행)
2. engine 작성 → tests/test_engine.py로 연습용 시나리오 3개 통과 확인
3. db, 로그인, 명단 올리기 → 학생과 관리자 화면 → 지원과 투표 → 마감
4. AI 배정(1~3차, 시간 제한, 검사, 앱 배정) → 확정
5. 로컬에서 연습용 시나리오를 화면으로 직접 해 보기 → Streamlit Cloud 배포 → 시크릿 창으로 확인
6. README.md 작성, 저장소 압축 파일 만들기, 마감 날 DB 사용
